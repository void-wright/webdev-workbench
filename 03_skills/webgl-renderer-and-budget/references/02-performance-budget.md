## 2. The performance budget

An example panel in a kitchen-equipment maker's resource library is 1200×560 CSS px. At the DPR cap of 1.5, that is 1800×840 = **1,512,000 device px**, so one full-panel layer draws **90.72 million device pixels per second at 60 fps**. This is pixel-count arithmetic, not a measurement of GPU capacity.

| Item | Rule | Evidence and status |
|---|---|---|
| **Frame budget** | 16.7 ms at 60 Hz (8.3 ms at 120 Hz); a minimum target of 50 fps means ≤20 ms. 33.3 ms is the degrade threshold, never a target | Frame intervals are computed from refresh rates. The minimum target and degrade threshold are proposed acceptance criteria, not measured results. |
| **Degrade trigger** | First 5 frames average >33 ms: back to the poster. A later 10-frame sample averaging >33 ms: cut particles. **No continuous dynamic-resolution controller**: one-shot tier-down only | PROPOSAL. Validate both sampling windows on target devices. For a mostly idle decorative panel, repeated resolution changes can create visible instability without enough benefit to justify the controller. |
| **DPR cap** | `Math.min(devicePixelRatio, 1.5)` for the canvas; HTML/SVG keep native DPR. On mobile, start at 1.25 if measurements support it | PROPOSAL. This is a cap, not a floor. Pixel count scales with DPR squared: reducing DPR from 3 to 1.5 removes 75% of pixels; reducing it from 2 to 1.5 removes 43.75%. These reductions do not guarantee equivalent frame-time improvements. |
| **Fill-rate (spec)** | Budget **overdraw** (pixels drawn more than once), not sprite count | Peak hardware specifications do not establish a usable layer budget. Bandwidth, blending, shader work and sprite coverage affect actual cost. Measure the complete panel on target hardware. |
| **Particle and thread caps** | Proposed ceiling: **≤300 stars, ≤500 connecting lines, ≤20,000 particles** per panel. Per-width caps below remain proposals until measured | PROPOSAL. These are design limits, not supported-device guarantees. A small number of large translucent sprites can cost more than many tiny particles. |
| **Particle caps by viewport width** (PROPOSAL) | <560 px: 120 stars / 150 connecting lines / 3k particles · 560-1023: 200 / 300 / 8k · 1024-1679: 300 / 500 / 15k · ≥1680: 300 / 500 / 20k | PROPOSAL. Viewport width is a layout input, not a reliable measure of GPU capability. Replace these starting limits with caps supported by representative device tests. |
| **Bundle ceiling** | **≤200 KB gzip hard ceiling**; **≤30 KB per layer target** | Proposed transfer budgets. Count the dependencies introduced by the effect. A hard ceiling is not permission to spend the entire allowance on one decorative element. |
| **Parse / compile** | Keep each layer to a handful of small programs; check `COMPLETION_STATUS_KHR` where available | Parse, compile and link costs depend on the bundle, shader complexity, browser and device. Measure them rather than assuming a library name guarantees a particular startup time. |
| **Texture formats** | Background artwork = AVIF/WebP in HTML via `astro:assets`, never a texture for this design. Star sprite baked once at boot (Canvas2D, 32-64 px) or a 32×32 PNG. Optional blue-noise texture: 64×64 PNG with a verified reusable licence. Render targets: probe R16F → RG16F → RGBA16F → RGBA8 + dither on a 4×4 FBO. **No KTX2** when there are no large textures to compress | PROPOSAL. Keep static artwork in the document and reserve GPU resources for the animated overlay. Check framebuffer completeness for each candidate format. Measure actual asset bytes; dimensions alone do not determine compressed size. |
| **Start on first interaction** | Desktop: `pointerenter` or `focusin` on the **panel element** (the canvas slot is `pointer-events:none`). Touch: first `pointerdown` toggles a class only; heavy work waits until after the next paint. **Never on load**, never Astro `client:visible`/`client:idle` for this interaction-only policy. Reduced motion or Save-Data: never start the decorative animation | The parent receives interaction while the canvas remains transparent to pointer events. INP covers qualifying click, tap and keyboard interactions, not hover or scrolling, but heavy work triggered by any event can still block subsequent input. Yield before initialization work. |
| **Off-screen pause** | `IntersectionObserver` threshold **0.1**; stop rAF fully; on re-entry reset `lastT = performance.now()` **before** requesting the frame and clamp dt | PROPOSAL for the visibility threshold. Resetting the clock prevents time spent off-screen from becoming one large simulation step. |
| **Visibility and battery** | `visibilitychange` stops the loop; render on demand once motion energy < ε; Save-Data → no automatic GPU startup; do not depend on `deviceMemory` or `prefers-reduced-data` for essential decisions | Treat optional browser signals as enhancements. Define ε for the animation and stop scheduling frames when motion has settled. |
| **dt clamp** | ≤0.1 s for analytic motion; springs take fixed 1/120 s sub-steps, at most 1/30 s per frame | PROPOSAL. Choose integration limits by motion type. Analytic motion and numerical spring simulation have different stability needs; cap catch-up work after a stall. |
| **Long tasks at 4× CPU** | No task >50 ms after the boot interaction; INP <200 ms; boot sliced across macrotasks | Acceptance targets, not measured results. Use a browser test with 4× CPU throttling to inspect startup long tasks, and test qualifying interactions separately. Hover timing alone does not establish INP. |
| **LCP / CLS** | Use the poster `<img>` as the intended LCP candidate, never the canvas (canvas is not an LCP candidate; inline `<svg>` is not either, but `<img src="…svg">` can be). Reserve space with `aspect-ratio`/min-height; fade with opacity; use `visibility:hidden`, not `display:none`, when hiding content whose layout space must remain | Verify the actual LCP element in the rendered page. The static poster supplies visible content before WebGL starts; reserved space prevents the transition from shifting surrounding content. |
| **Glow cost** | Sprites, no post-processing chain | PROPOSAL for decorative panels. Baked halos avoid additional full-panel passes, but large translucent sprites still incur overdraw. Measure their coverage and blending cost; do not assume a universal millisecond cost. |
| **Half-float positions** | Do not store stateful positions in half-float; use analytic motion (or RGBA32F, unfiltered, where supported) | Half-float spacing is 1.0 across 1024-2048. Repeatedly adding a 0.08-0.17 px/frame drift to stored positions in that range can round back to the same value, causing motion to stick. Integer representability does not guarantee sufficient precision for fractional updates. |
